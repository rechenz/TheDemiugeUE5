## 一、分层总览

依赖方向**严格单向向下**,且**零例外**。

```
L10 横切      存档/版本迁移、调试工具、成就统计、难度配置、教程、模组、网络同步
L9  表现      UI 数据绑定、表现事件映射、相机、本地化
L8  Agent     Agent编排、知识视图、提议仲裁★、记忆、异步队列、内容校验
L7  叙事      任务系统★、对话、关系声望、剧情编排
L6  世界      世界标记★、战斗时序、场景关卡、空间查询、生成刷怪、传统AI
L5  行为      意图与命令、效果 Effect★、技能、状态效果、目标选择、冷却
L4  物品      物品定义、背包容器、装备、掉落、商店交易、合成
L3  条件      条件引擎(DSL + Provider 注册)★
L2  数值      属性、修饰器、数值依赖图、结算管线、资源
L1  实体      实体注册表、组件、标签、系统调度器
L0  基础      时钟、确定性随机、句柄/生命周期、配置数据、输入采集、日志
```

### 1.1 关于"零例外"

早期版本把"任务系统订阅事件总线"和"条件引擎 Provider 注册"列为两处例外。**这是错的**,原因是我混淆了两个方向:

| | 编译期依赖 | 运行时调用 | 是否违反单向 |
|---|---|---|---|
| 任务订阅事件总线 | L7 → L0(向下) | L0 回调 L7(反向) | **否** |
| 条件引擎 Provider 注册 | L7 → L3 的接口(向下) | L3 调用 L7 的实现(反向) | **否** |

**判据:只要下层只依赖自己定义的接口、不含上层的任何符号,编译期依赖就是纯向下的。** 运行时反向调用(回调、注册、观察者)不构成依赖违规。

所以:**零例外。** 任何需要"例外"的设计,都是接口没放对位置。

## 二、依赖规则细则

### 2.1 数据引用 ≠ 代码依赖

L4 的掉落表里写 `Region = "Forest"`,L4 的代码不需要 include L6 的空间查询。**字符串引用不构成依赖。**

真正的判据是:**执行权在哪一层?**
- 掉落表的**数据**在 L4 —— 没问题
- 掉落的**判定执行**(要查区域、查玩家状态)必须在 L6 —— 因为它在读 L6 的上下文

**通则:低层只存放描述数据(模板/ID/字符串),执行权移交高层。**

### 2.2 事件总线是通知,不是变更通道

**契约(必须写死):**
- 事件订阅者**只能读状态**,不得直接改状态
- 任何状态变更**必须**通过 L5 的 Effect 系统发起
- 违反此契约的代码在 Code Review 中一律打回

事件总线是**通知机制**,不是**变更机制**。这不是双通道,是一条变更通道 + 一个广播喇叭。

### 2.3 Effect 的边界定义

"一切状态变更是 Effect"这句太绝对。准确定义:

> **Effect = 可归因到某个 instigator、符合游戏规则、需要被记录/回放/同步的状态变更。**

| 操作 | 是 Effect? | 归属 |
|---|---|---|
| 造成伤害、治疗、加 Buff | ✅ 是 | L5 Effect |
| 获得/失去物品 | ✅ 是 | L5 Effect |
| 设置世界标记 | ✅ 是 | L5 Effect(可归因、要存档、要触发连锁) |
| 推进任务状态 | ✅ 是 | L5 Effect |
| 刷怪 | ❌ 否 | L6 世界模拟(Spawner 驱动) |
| 世界时间推进 | ❌ 否 | L6 世界模拟 |
| 场景流式加载 | ❌ 否 | L0/L6 平台行为 |
| 传统 AI 决策 | ❌ 否 | L6。决策本身不是变更;决策**产生的行为**才走 Effect |

**分界线:系统驱动的模拟 vs 参与者驱动的行为。** 前者是环境演化,后者是 Effect。

## 三、系统清单

优先级:**P0** = 不写没法开始 / **P1** = 核心玩法必须 / **P2** = 内容量上来才要 / **P3** = 锦上添花

### L0 基础层

- [ ] **P0 时钟系统** — **唯一天真源**。真实时间 / 游戏时间 / 回合三个时钟在此统一,只暴露查询接口。L5 的冷却、L4 的限时道具一律向这里取时间,**不得自带计时器**
- [ ] **P0 输入采集** — 硬件事件 → 原始输入意图。纯平台层,不认识任何游戏规则
- [ ] **P0 事件总线** — 发布/订阅。**契约:订阅者只读,变更必须走 Effect**
- [ ] **P0 配置数据层** — DataTable / DataAsset 加载、校验、热重载。所有数值不准硬编码
- [ ] **P0 句柄与生命周期** — 世代索引(Generational Index):`{Index, Generation}`,防悬空引用
- [ ] **P1 确定性随机** — 种子化 RNG,可存档。同种子同结果,不然 bug 无法复现
- [ ] **P1 日志与调试控制台** — 分级日志 + 运行时作弊命令
- [ ] **P2 对象池** — 高频生成物(子弹/特效/伤害数字)复用

### L1 实体层

- [ ] **P0 实体注册表** — ID 分配、查询、销毁。注意:数据实体不是 Actor
- [ ] **P0 组件系统** — 数据切片,按需组合
- [ ] **P1 标签系统** — 条件判断、目标筛选全靠它
- [ ] **P1 系统调度器** — Tick 分阶段 + 优先级 + 可暂停

### L2 数值层

- [ ] **P0 属性系统** — 基础值 / 当前值 / 上限,带脏标记
- [ ] **P0 修饰器系统** — 加法区 / 乘法区 / 覆盖区,**必须追踪来源**,否则脱装备卸不干净
- [ ] **P1 数值依赖图** — 派生属性(攻击力 = 基础 × 等级系数 + 装备)。**惰性求值 + 脏传播**,不要全图重算
- [ ] **P1 结算管线** — 伤害/命中/暴击/抗性,固定顺序的可插拔管道
- [ ] **P1 资源系统** — HP/MP/耐力,消耗、恢复、回复速率

### L3 条件层

- [ ] **P0 条件引擎** — 条件 DSL(AND/OR/NOT 嵌套 + 原子谓词)+ **Provider 注册制**
  - 条件类型:等级、属性比较、持有物品、任务状态、世界标记、声望、时间、概率
  - **接口定义在 L3,实现由各层反向注册** → 编译期依赖仍向下
  - 求值时记录依赖项,支持**响应式重算**
- [ ] **P1 条件文案生成** — "需要等级 10(当前 8)",供 UI 显示

### L4 物品层

> **本层只存放描述数据与容器逻辑。掉落判定、商店定价校验、物品效果执行的「执行权」全部移交 L6 / L5。**

- [ ] **P0 物品定义/原型** — 数据驱动模板。效果以 **Effect ID 字符串**引用,不 include L5
- [ ] **P0 背包容器** — 槽位、堆叠、容量、排序、增删改查
- [ ] **P1 装备系统** — 槽位、穿戴校验、属性注入与卸载
- [ ] **P2 掉落表** — 权重随机、保底、条件掉落。**数据在此,判定在 L6**
- [ ] **P2 商店/交易** — 定价、库存刷新、买卖校验。**数据在此,校验在 L6**
- [ ] **P3 合成/制作** — 配方图、材料消耗

### L5 行为层

- [ ] **P0 效果系统(Effect)★** — **唯一的状态变更通道**。可序列化、可回放、可校验、可撤销
  - **执行栈深度限制 + 重入保护**:Effect 触发 Effect(暴击→溅射→连锁)必须有深度上限与环检测,否则单次触发可卡死游戏
  - **执行顺序确定化**:同一批次 Effect 的结算顺序必须确定,否则回放对不上
- [ ] **P0 意图与命令** — 原始输入 → 游戏意图 → 命令 → Effect。意图生成在此,**输入采集在 L0**
- [ ] **P1 技能/能力系统** — 消耗 + 冷却(时间取 L0)+ 目标选择 + 效果列表
- [ ] **P1 目标选择器** — 单体/范围/扇形/条件筛选(条件走 L3)
- [ ] **P1 状态效果(Buff/Debuff)** — **只声明「持续时长 + 触发时机枚举」**,时间推进由 L0/L6 显式注入;含堆叠规则、互斥、驱散
- [ ] **P2 冷却与消耗管理** — 独立于技能,便于统一 UI 与存档
- [ ] **P3 命令撤销/回放** — 战术类 RPG 值得做,动作类可跳

### L6 世界层

- [ ] **P0 世界标记(World Flags)★** — 全局状态。**写入走 Effect**,读取供 L3 条件引擎
- [ ] **P1 战斗时序** — 回合制/实时、行动序列、胜负判定。**只提供时序事件,不提供时钟**
- [ ] **P1 场景/关卡管理** — 加载流、切换、持久化边界
- [ ] **P1 空间查询** — 范围、视线、寻路。UE 自带的可直接用
- [ ] **P2 生成/刷怪** — 世界模拟,非 Effect
- [ ] **P2 传统 AI** — 行为树或 Utility。与 L8 Agent 分工:常规行为走此层,开放语义决策走 L8

### L7 叙事层

- [ ] **P0 任务系统★** — 七块拼成:
  - [ ] 任务图(前置/解锁/互斥 + 可用性传播)
  - [ ] 状态机(未接取→可接取→进行中→可交付→完成/失败/放弃)
  - [ ] 目标追踪(击杀/收集/到达/对话/限时)
  - [ ] 条件集成(走 L3 条件引擎)
  - [ ] 奖励发放(**必须走 Effect**,不准自己写背包)
  - [ ] 任务日志 / HUD 追踪
  - [ ] **定义(模板)与实例(运行时)分离** ← 不做这个,日常任务必炸
  - **P0 的是「数据结构可静态推导」;校验器工具本身是 P1**
- [ ] **P1 任务图静态校验器** — Editor 工具:
  - 环检测 / 可达性 / 死锁(互斥任务互为前置) / 悬空引用 / 奖励经济检查
  - **Agent 生成的任务必须过它才能进图**
- [ ] **P1 对话系统** — 节点图 + 条件分支 + Effect 触发
- [ ] **P2 关系/声望** — 阵营、好感度、态度影响
- [ ] **P3 剧情编排/过场** — 导演层

### L8 Agent 层

> **本层有四条硬约束,见第五章。违反任何一条,架构即失效。**

- [ ] **P0 效果提议仲裁★** — LLM 输出 → 校验 → Effect → 世界状态。**Agent 只能提议,规则引擎是唯一裁判**
- [ ] **P0 知识视图** — 上下文构建时**按角色已知集合裁剪**。NPC 不得看到未解锁的世界标记、未来剧情、他人隐私
- [ ] **P0 提议版本戳** — 提议必须携带所依据的世界快照版本号,应用前校验
- [ ] **P1 Agent 编排层** — Agent 注册、角色定义、调度
- [ ] **P1 结构化输出约束** — JSON Schema / Tool Calling。不准自由文本再解析
- [ ] **P1 LLM 内容校验器** — 生成的物品/NPC/任务过静态检查才能进图
- [ ] **P1 记忆系统** — 短期 / 长期 / 检索。**只存主观视角,schema 纳入存档版本迁移**
- [ ] **P2 异步任务队列 + 降级** — LLM 慢,不能卡帧;超时降级到规则驱动
- [ ] **P2 缓存与成本控制** — 同状态同 prompt 命中缓存

### L9 表现层

- [ ] **P1 UI 框架 / 数据绑定** — ViewModel 模式,**模型不持有 UI 引用**
- [ ] **P1 表现事件映射** — 游戏事件 → 动画/特效/音效。表现层只订阅,不改状态
- [ ] **P2 相机控制** — 跟随、锁定、震屏
- [ ] **P3 本地化** — 越早越好,后补成本极高

### L10 横切层

- [ ] **P0 存档 / 序列化 / 版本迁移★** — **策略必须在骨架期定型**,见第四章
- [ ] **P1 调试工具** — 状态查看器、Gizmo、时间旅行回放
- [ ] **P2 成就/统计** — 埋点式,独立于玩法逻辑
- [ ] **P2 难度/平衡配置** — 数值倍率分层
- [ ] **P3 教程/引导**
- [ ] **P3 模组/扩展** — 只有明确要做才上
- [ ] **P3 网络同步** — 只有多人项目才需要;单机跳过

## 四、存档策略(骨架期必须定型)

**为什么前置:既然一切变更走 Effect,"日志还是快照"这个选择决定了 Effect 的接口形态。等到第 7 步再定,要重构整条变更链路。**

### 选定方案:Effect 日志 + 周期快照

```
存档 = 最近一次全量快照 + 之后的 Effect 日志(增量)
```

| 部分 | 内容 |
|---|---|
| **快照** | 实体表、属性、背包、世界标记、任务实例、Agent 记忆 |
| **日志** | 快照之后的全部 Effect(含参数、instigator、时间戳、随机种子状态) |
| **版本** | 每个存档带 schema version,迁移函数一条版本一条 |

**收益:**
- 读档 = 载入快照 + 重放 Effect → 天然可验证(重放结果必须与存档时一致)
- 回放 / 撤销 / 调试全部白送
- 网络同步可复用同一套

**代价(必须在 L5 锁死的约束):**
- Effect 必须**完全可序列化**
- Effect 执行必须**确定**(配合 L0 的种子化 RNG,禁止跨层直接调 `rand()`)

**版本迁移:** 每个 schema 版本一条迁移路径,v1→v2→v3 链式升级。**禁止跳版本迁移。**

## 五、Agent 接入四条硬约束

这一层是项目差异化所在,也是**最容易把架构搞塌的地方**。

### 约束 1:只读 + 只提议

Agent **不得直接修改任何世界状态**。它只能:
1. 通过**知识视图**读取允许它看到的状态
2. 输出**结构化的 Effect 提议**
3. 由规则引擎校验后,决定是否执行

### 约束 2:知识视图(信息隔离)

扮演 NPC 的 Agent 不能是一个全知视角。

```
世界状态全集
    ↓ 按「该角色已知集合」裁剪
知识视图 = 该 NPC 亲历的事件 + 被告知的信息 + 它的身份该知道的常识
    ↓
Prompt
```

**未解锁的世界标记、未来的任务状态、其他角色的秘密,一律不得进入上下文。** 否则 NPC 会"未卜先知",玩家一眼就能看出来。

### 约束 3:乐观并发(版本戳)

LLM 是异步的。等它返回时,世界可能已经变了。

```
t0: Agent 读取世界快照,版本 = 42
t1: 玩家杀了那个 NPC
t2: Agent 返回提议「把信件交给该 NPC」   ← 基于版本 42 的旧世界
t3: 应用前校验:当前版本 = 43 ≠ 42 → 拒绝
```

**提议必须携带快照版本,应用前校验。** 校验失败的处理见约束 4。

### 约束 4:仲裁失败的反馈回路

提议被拒后**必须有明确策略**,否则 NPC 会突然沉默或无限重试。

| 拒绝原因 | 处理 |
|---|---|
| 规则违规(目标不可达、条件不满足) | 把拒绝原因**回灌**给 LLM 重新提议,次数上限 2 次 |
| 版本冲突 | 重新读取最新状态视图,**重新提议**,上限 2 次 |
| 越权(试图修改不该改的) | **直接丢弃 + 记录日志**,不回灌(防止绕过) |
| 超限(次数用尽) | 降级到规则驱动行为或返回安全默认值 |

### 附带约束:记忆不是第二个真相源

**可从世界状态推导的事实,一律不进记忆。** 记忆只存**主观视角**:印象、态度、八卦、承诺。

存了"某 NPC 已死"这种客观事实,就会和 World Flags 打架。而且**记忆的 schema 也必须有版本迁移**——它和存档是同一等级的持久化数据。

## 六、关键设计决策(已定)

### 1. 依赖是「拉取式条件」,不是「推送式硬连线」

```cpp
// ✗ 硬连线:任务A知道任务B存在,双向耦合
OnQuestComplete("Q001") { UnlockQuest("Q002"); }

// ✓ 单方面声明需求,依赖图可从配置静态推导
Q002.Prerequisites.Add(FQuestStateCondition("Q001", EQuestState::Completed));
```

这样才做得了拓扑排序、环检测、死锁检测——**编译期**就能查出来。

### 2. 条件引擎依赖倒置

条件引擎在 L3,却要查 L7 的任务状态。解法:

```cpp
class IConditionProvider {
    virtual bool Evaluate(const FCondition& Cond) = 0;
};

QuestSystem     -> Register("QuestState",  ...);
InventorySystem -> Register("HasItem",     ...);
StatSystem      -> Register("StatCompare", ...);
```

引擎只认接口,具体系统反向注册。**一套条件 DSL 全项目复用。**

### 3. 定义与实例分离

```
QuestDefinition (模板,数据驱动,只读)
      ↓ 实例化
QuestInstance   (运行时状态,可存档,可多份)
```

目标还要区分**类型引用**("杀3个哥布林")和**实体引用**("保护张三")。

### 4. Effect 是唯一的状态变更通道

所有状态变化都是 Effect 对象。免费收益:存档、回放、网络同步、调试、撤销。

**Agent 输出绝对不能直接改世界状态,只能提议 Effect。**

### 5. 数值依赖用惰性求值

脏标记 + 按需重算。玩家完成一个任务,只重算它的直接下游,不要全图重算。

## 七、实施顺序

**别横向铺系统,先竖着打通一条线。**

```
输入(L0) → 意图(L5) → 技能(L5) → Effect(L5) → 属性变化(L2)
                                              ↓
                                    事件总线 → UI(L9)
                                              ↓
                     任务目标追踪(L7) → 完成 → Effect 发奖励 → 背包(L4)
                                              ↓
                                    快照 + Effect日志(L10) → 读档 → 状态一致
```

| 阶段 | 内容 | 为什么这个顺序 |
|---|---|---|
| **0** | L0 三件套(时钟/句柄/事件总线)+ 输入采集 + 配置层 | 没有这些,后面全是重写 |
| **1** | L1 实体 + L2 属性/修饰器 | 能造出一个有数值的角色 |
| **2** | L5 Effect + **存档策略定型** | Effect 接口由存档策略决定,不能倒过来 |
| **3** | L9 UI 绑定 + 表现事件映射 | 能看见数值变化,闭环成一半 |
| **4** | L4 物品 + L3 条件引擎 | 能持有物品、能做判断 |
| **5** | **L8 最小 Agent 竖切★** | **提前验证四条约束**,见下 |
| **6** | L7 任务 + L6 世界标记 | 能接任务、做任务、交任务、拿奖励 |
| **7** | L10 存档落地(快照 + 日志 + 迁移) | 存了能读回来 |
| **8** | 横向铺开(商店/合成/声望/成就/对话…) | 加插件,不改地基 |

### 阶段 5 为什么必须提前

项目名为 **TheDemiugeAgent**,Agent 是核心差异化。**如果等到最后才接 Agent,架构已经冻结,四条约束任何一条不满足都要动地基。**

**最小竖切 = 一个 NPC + 一条提议 Effect + 一次裁决拒绝 + 一次版本戳冲突。**

验证四件事:
1. 知识视图能否正确裁剪(看不到未解锁标记)
2. 提议能否被规则引擎拒绝
3. 版本戳冲突能否被检出
4. 拒绝原因能否回灌并让 LLM 修正

**这四件事过了,Agent 才敢往深做。**

## 八、UE5 落地建议

- **GAS 用不用**:它的 Attribute / GameplayEffect / GameplayTag 恰好覆盖 L2 + L5 大半。但它是黑盒,深度定制会撞墙。**建议先抄设计思想,自己实现轻量版**——你做的是架构,不是 GameJam 原型
- **别用 Actor 当数据实体**:背包里 500 个物品不该是 500 个 Actor。数据层纯 C++,Actor 只是表现层代理
- **数据模板与运行时实体的正确姿势**:`UDataAsset` 作**只读模板**,由 Subsystem 强引用常驻(它本身是受 GC 管理的 `UObject`,靠 Subsystem 的引用保证不被回收);**运行时实体是纯 C++ 结构体 + `FHandle`**,两者按 id 关联。这样运行时不依赖 GC,也不会有 500 个 UObject
- **Subsystem 当系统容器**:`UGameInstanceSubsystem` 管全局(存档/配置/事件总线),`UWorldSubsystem` 管场景系统。别搞 Singleton 满天飞
